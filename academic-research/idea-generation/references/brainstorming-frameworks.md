# 10 种发想框架详细说明

本文件提供 idea generation 流程中使用的十种发想框架之详细说明。每个框架包含定义、操作步骤、范例与适用场景。

---

## 框架 1：Problem-First（从问题出发）

### 定义

从实际存在的问题、痛点或未被满足的需求出发，逆向寻找可能的研究方向。这是最直觉的发想方式，确保研究具有实际意义。

### 操作步骤

1. **列举问题来源**
   - 回顾自己在研究或实务中遇到的困难
   - 浏览相关领域的论坛、问答网站（如 Stack Overflow、Reddit）
   - 阅读近期论文的 limitations 段落
   - 访谈领域的实务工作者

2. **问题分类与排序**
   - 将问题依据严重程度、影响范围、频率进行分类
   - 优先关注高频且高影响的问题

3. **问题拆解**
   - 将大问题拆解为可研究的子问题
   - 找出问题的根本原因（root cause），而非表面症状

4. **可研究性检验**
   - 这个问题能否被形式化为一个研究问题？
   - 是否有可量化的评估指标？
   - 是否有可获取的资料？

### 范例

- **问题**：大型语言模型在长文本上的表现显著下降
- **拆解**：注意力机制的计算复杂度、位置编码的外推性、上下文资讯的遗失
- **研究方向**：设计新的位置编码方案，使模型能外推至训练长度以外的文本

### 适用场景

- 希望研究具有明确实用价值时
- 对某个领域有深入实务经验时
- 寻找能快速获得社群认可的研究题目时
- 撰写以问题驱动为主的学位论文时

---

## 框架 2：Solution-First（从技术出发找应用）

### 定义

从一个新的技术、演算法或工具出发，思考它可以被应用到哪些场景或问题上。这种方式适合当你已经掌握一个有潜力的技术，但尚未找到最佳应用场景。

### 操作步骤

1. **技术特性分析**
   - 这个技术的核心优势是什么？
   - 它在什么条件下表现最好？
   - 它的限制是什么？

2. **应用场景搜索**
   - 哪些领域有类似的需求结构？
   - 哪些现有方法因为缺乏这个技术特性而受限？
   - 是否有新兴的应用场景尚未被充分探索？

3. **适配性评估**
   - 技术的输入输出格式是否匹配目标问题？
   - 是否需要大幅修改才能适用？
   - 计算资源需求是否合理？

4. **差异化定位**
   - 相比现有方法，这个技术能带来什么独特的优势？
   - 这个优势是否足够显著？

### 范例

- **技术**：Diffusion Model 的去噪机制
- **特性**：能从杂讯中逐步恢复结构化资讯
- **应用探索**：除了图像生成，能否用于分子结构生成？蛋白质折叠？城市规划？
- **研究方向**：将 Diffusion Model 应用于程式码修复，将有 bug 的程式码视为「杂讯版本」

### 适用场景

- 刚学会一个新技术，想深入探索其潜力时
- 技术导向的研究团队寻找应用方向时
- 希望做跨领域应用的研究时
- 某个技术在原始领域已趋饱和，需要寻找新战场时

## 框架 3：抽象阶梯（Abstraction Ladder）

### 定义

在不同的抽象层次之间移动思考。向上抽象可以看到问题的本质与共通性，向下具体化可以找到新的实例与应用。这个框架帮助你跳脱当前的思考层次，发现隐藏的连结。

### 操作步骤

1. **确定起点**
   - 选择一个你熟悉的具体问题或方法

2. **向上攀升（抽象化）**
   - 问：「这个问题的本质是什么？」
   - 问：「这属于哪一类更广泛的问题？」
   - 问：「背后的基本原理是什么？」
   - 持续向上直到到达足够抽象的层次

3. **横向移动**
   - 在同一抽象层次上，思考是否有其他实例
   - 这个原理还适用于哪些情境？

4. **向下降落（具体化）**
   - 从新的抽象概念出发，向下具体化
   - 这个原理可以如何实现？
   - 在什么资料集或任务上可以验证？

### 范例

```
具体问题：机器翻译中的罕见词处理
    ↑ 抽象
稀有事件的处理（长尾分布问题）
    ↑ 抽象
如何从有限样本中学习？（小样本学习）
    → 横向移动
医疗影像中的罕见疾病辨识
    ↓ 具体化
研究方向：利用语言模型的知识增强罕见疾病影像的辨识
```

### 适用场景

- 感觉在同一个层次打转、找不到突破口时
- 想要发现两个看似无关领域之间的连结时
- 希望将一个具体的成功经验推广到更多场景时
- 需要为研究找到更深层的理论动机时

## 框架 4：矛盾猎寻（Contradiction Hunting）

### 定义

主动寻找现有研究中的矛盾、冲突假设、未被质疑的预设或不一致的实验结果。矛盾往往是新知识的入口，指向我们理解不足的地方。

### 操作步骤

1. **假设盘点**
   - 列出你的研究领域中被广泛接受的假设
   - 问自己：这些假设的证据有多强？
   - 是否有反例被忽略了？

2. **结果比对**
   - 比较不同论文在类似实验上的结果
   - 是否有不一致的发现？
   - 不一致是否源于实验设定的差异？

3. **理论 vs 实践**
   - 理论预测与实际表现是否一致？
   - 哪些理论上应该有效的方法在实践中失败了？
   - 哪些理论上不应该有效的方法反而成功了？

4. **深挖矛盾**
   - 矛盾的根本原因是什么？
   - 解决矛盾是否能带来新的理解？
   - 能否设计实验来厘清矛盾？

### 范例

- **矛盾**：Transformer 理论上的表达能力无限，但在简单的计数任务上却表现不佳
- **深挖**：位置编码方式限制了模型的长度泛化能力
- **研究方向**：设计能正确处理计数与算术推理的架构改进

### 适用场景

- 对一个领域有深入了解，能察觉微妙的不一致时
- 阅读大量论文后发现结论互相矛盾时
- 重现他人实验时发现与原文不符时
- 希望做批判性、挑战现有认知的研究时

## 框架 5：跨领域嫁接（Cross-Domain Transfer）

### 定义

将一个领域的成功方法、概念或理论框架引入另一个领域。跨领域嫁接是创新的重要来源，因为不同领域往往面对结构上相似的问题，但使用不同的解决方案。

### 操作步骤

1. **建立知识库**
   - 广泛阅读不同领域的综述文章
   - 参加跨领域的学术活动
   - 与不同领域的研究者交流

2. **结构性类比**
   - 你的领域中的问题，在其他领域是否有对应？
   - 其他领域的经典方法，能否解决你领域的问题？
   - 两个领域的资料结构是否有相似性？

3. **迁移可行性评估**
   - 方法的前提假设在新领域是否成立？
   - 需要哪些调整来适配新领域？
   - 跨领域迁移是否带来额外的优势？

4. **验证计划**
   - 如何在新领域中评估迁移效果？
   - 是否有合适的 baseline 来比较？

### 范例

- **来源领域**：流体力学中的 Navier-Stokes 方程的数值解法
- **目标领域**：大规模图网路上的资讯传播模拟
- **类比**：资讯流动 ≈ 流体流动
- **研究方向**：借用流体力学的多尺度模拟方法来加速图网路上的讯息传递

### 适用场景

- 具有多领域背景的研究者
- 当前领域的方法已趋成熟，需要外部灵感时
- 发现两个领域有相似问题结构时
- 希望做开创性的跨领域研究时

---

## 框架 6：What Changed（关注最近的技术变化）

### 定义

关注最近发生的技术突破、资源变化或社会环境变化，思考这些变化开启了哪些原本不可能的研究方向。好的研究 idea 往往出现在变化的交界处。

### 操作步骤

1. **盘点近期变化**
   - 最近 6-12 个月有哪些重要的技术突破？
   - 哪些新的资料集或工具被释出？
   - 硬体能力有什么变化？
   - 社会需求或政策有什么新趋势？

2. **影响分析**
   - 这个变化使什么原本不可能的事情变得可能？
   - 这个变化推翻了哪些旧的限制条件？
   - 这个变化创造了哪些新的需求？

3. **时机评估**
   - 这个方向是否处于合适的时间点？
   - 是太早（基础设施不成熟）还是太晚（已经饱和）？
   - 竞争者的动态如何？

4. **快速原型验证**
   - 能否用最少的资源做一个概念验证？
   - 初步结果是否支持你的假设？

### 范例

- **变化**：开源大型语言模型的参数规模与能力显著提升
- **新可能**：原本需要闭源 API 才能做的研究，现在可以在本地进行深入分析
- **研究方向**：对开源模型进行机制性分析（mechanistic interpretability），理解其内部知识表示

### 适用场景

- 追踪技术前沿的研究者
- 希望做有时效性、能快速发表的研究时
- 新技术刚出现，尚未被充分探索时
- 对「为什么是现在？」这个问题有清晰答案时

## 框架 7：失败分析（Failure Analysis）

### 定义

从失败的尝试中学习，将失败视为发现新研究方向的线索。失败往往揭示了我们理解的盲区，而这些盲区正是值得研究的地方。

### 操作步骤

1. **收集失败案例**
   - 自己过去失败的实验或被拒的论文
   - 领域中已知的失败尝试
   - Benchmark 上表现特别差的案例（error analysis）
   - 工业界部署后遇到的问题

2. **失败归因**
   - 失败的根本原因是什么？
   - 是方法问题、资料问题、还是问题本身太难？
   - 失败是可修复的，还是需要全新的方法？

3. **机会辨识**
   - 这个失败是否指向一个未被充分研究的子问题？
   - 修复这个失败是否能带来显著的改进？
   - 是否有新的技术可以克服以前的限制？

4. **解决方案构想**
   - 根据失败原因，构想可能的解决方案
   - 是否有其他领域遇到类似的失败并找到了解决方案？

### 范例

- **失败案例**：Few-shot learning 在分布外（OOD）资料上表现崩溃
- **失败归因**：模型过度依赖 spurious features，在少样本设定下更为严重
- **研究方向**：设计对 spurious features 具有鲁棒性的 few-shot learning 方法

### 适用场景

- 从自己的失败经验中提炼研究方向时
- 做某个任务的 error analysis 后发现系统性问题时
- 阅读论文的 limitations 段落时受到启发
- 希望做有深度的、解决根本问题的研究时

## 框架 8：简单性测试（Simplicity Test）

### 定义

用更简单的方法挑战目前复杂的主流方法，测试那些复杂性是否真的必要。如果一个简单的方法能达到类似的效果，那么复杂方法的价值就需要被重新评估。

### 操作步骤

1. **选择目标**
   - 选择一个近期提出的、被认为有效但相当复杂的方法
   - 或选择一个 SOTA 系统，分析其各组件

2. **简化实验**
   - 移除某些组件，观察效果变化（ablation 的延伸）
   - 用更简单的替代方案取代某些组件
   - 设计最简化的 baseline

3. **公平比较**
   - 确保比较条件公平（相同的资料、超参数搜索预算等）
   - 测量不仅是效能，也包括效率（速度、记忆体、能耗）

4. **结果分析**
   - 如果简单方法表现接近：什么是真正重要的组件？
   - 如果简单方法表现差距大：复杂性的来源与价值是什么？
   - 两种情况都能产生有价值的研究贡献

### 范例

- **目标**：某个使用多个预训练模型、复杂融合机制的多模态系统
- **简化**：只使用单一模型 + 简单的线性映射
- **发现**：在多数情境下，简单方法达到 90% 的效能，但只需 10% 的计算量
- **研究方向**：分析何时复杂的融合机制是真正必要的

### 适用场景

- 对某个领域的「军备竞赛」持怀疑态度时
- 计算资源有限，需要高效率的方法时
- 希望做有批判性、能引发讨论的研究时
- 撰写分析型论文（analysis paper）时

## 框架 9：利害关系人旋转（Stakeholder Rotation）

### 定义

从不同利害关系人（使用者、开发者、决策者、受影响者等）的角度重新审视一个问题或技术。不同角色有不同的需求、限制和价值观，这些差异可以揭示被忽略的研究方向。

### 操作步骤

1. **辨识利害关系人**
   - 谁会使用这个技术？
   - 谁会部署和维护这个技术？
   - 谁会被这个技术的结果影响？
   - 谁会为这个技术付费？
   - 谁会监管这个技术？

2. **角色扮演**
   - 逐一站在每个利害关系人的角度思考
   - 他们最在意什么？最担心什么？
   - 他们的日常工作流程是什么？
   - 这个技术如何融入他们的工作？

3. **需求差异分析**
   - 不同利害关系人的需求是否有冲突？
   - 哪些需求目前被忽视了？
   - 满足这些需求需要什么样的研究？

4. **研究方向转化**
   - 将需求转化为可研究的问题
   - 优先处理影响面广且具可行性的问题

### 范例

- **技术**：自动程式码生成工具
- **开发者角度**：希望生成的程式码正确且高效
- **团队主管角度**：希望生成的程式码符合团队的风格规范
- **安全工程师角度**：担心生成的程式码是否有安全漏洞
- **新手程式设计师角度**：希望工具能同时教学，而非只给答案
- **研究方向**：自动程式码生成中的安全性保证机制

### 适用场景

- 研究具有社会影响的技术时
- 做人机互动（HCI）相关研究时
- 希望研究更有实际应用价值时
- 撰写涉及伦理考量的论文时

## 框架 10：组合/分解（Combine / Decompose）

### 定义

透过将现有方法组合或拆解来产生新的研究方向。组合可以创造具备多重优势的新方法；分解可以深入理解复杂系统的各个组件，并独立改进。

### 操作步骤

#### 组合路径

1. **列出候选方法**
   - 选择 2-3 个在不同方面有优势的方法
   - 确认它们解决的问题有重叠或互补的部分

2. **互补性分析**
   - 方法 A 的优势是否能弥补方法 B 的劣势？
   - 组合后是否能 1+1 > 2？
   - 组合的技术可行性如何？

3. **组合方式设计**
   - 串联（pipeline）：A 的输出作为 B 的输入
   - 并联（ensemble）：同时使用 A 和 B，融合结果
   - 混合（hybrid）：在 A 的架构中嵌入 B 的机制

#### 分解路径

1. **选择目标系统**
   - 选择一个复杂的、端到端的系统或方法

2. **组件辨识**
   - 这个系统由哪些核心组件构成？
   - 每个组件的功能是什么？
   - 组件之间的互动关系是什么？

3. **组件深入研究**
   - 某个组件是否可以被独立改进？
   - 某个组件是否可以用更好的替代方案？
   - 组件之间的互动是否被充分理解？

### 范例

#### 组合范例
- **方法 A**：Retrieval-Augmented Generation（擅长利用外部知识）
- **方法 B**：Chain-of-Thought prompting（擅长复杂推理）
- **组合**：检索相关知识后，使用链式推理来整合与应用
- **研究方向**：设计能根据问题复杂度动态决定是否检索、何时推理的统一框架

#### 分解范例
- **目标系统**：大型语言模型的 in-context learning 能力
- **组件辨识**：任务识别、模式匹配、知识提取、格式对齐
- **研究方向**：深入研究 in-context learning 中「任务识别」组件的运作机制

### 适用场景

- 希望做整合性的研究，统一多个方法时
- 希望深入理解复杂系统的运作机制时
- 两个独立的研究方向有交叉的潜力时
- 做系统设计（system paper）时

## 框架选择指南

| 你的状态 | 建议使用的框架 |
|----------|---------------|
| 有明确的问题但不知道怎么解决 | Problem-First, 失败分析 |
| 学了新技术想找应用 | Solution-First, What Changed |
| 感觉在同一层次打转 | 抽象阶梯, 跨领域嫁接 |
| 对主流方法存疑 | 矛盾猎寻, 简单性测试 |
| 想做有社会影响的研究 | 利害关系人旋转 |
| 想整合或深入分析 | 组合/分解 |
| 不确定，想广泛探索 | 至少选 3-5 个框架轮流使用 |

---

## 使用建议

1. **不要只用一个框架**：每个框架都有盲区，使用多个框架能覆盖更多角度
2. **先量后质**：在使用框架时先不要批判，尽量多产出
3. **记录过程**：记下每个框架触发的所有想法，即使看起来不成熟
